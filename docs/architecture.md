# Architecture

Browser → Next.js same-origin proxy → authenticated Fastify API → scheduler → isolated training process → environment / policy / trainer.

The control service owns durable run state and the managed Java process. It admits at most `MAX_CONCURRENT_RUNS` workers and `MAX_AGENTS` agents across workers, with up to 100 queued runs. Separate Node processes isolate model computation, Minecraft client traffic and failures from HTTP handling. Agent steps inside a worker execute concurrently; tick iterations never overlap. Minecraft connections are staggered per run by awaiting spawn for each agent.

The dashboard polls a bounded snapshot every two seconds; it does not crawl logs, worlds or checkpoint directories. A selected run loads its own metrics and logs separately. All browser commands use an allowlisted same-origin proxy. The bearer token stays on the server, never in client bundles. Both services bind to loopback by default. POST proxy requests require a matching Origin/Host. The proxy and CLI can connect to a remote runtime through `CONTROL_URL` using HTTPS and server-side credentials; a remote dashboard does not need shared data volumes. There is no user-account authentication, so deployed access remains private.

SQLite uses WAL, indexed run metric/log queries and bounded batch writes for agent state. Artifacts stream to per-run files; they are not accumulated in memory. Live sample rates are approximately one sample per second per run, plus two-second control metrics. Worker messages carry small typed payloads. Agent transitions go directly to the trainer hook rather than through the dashboard or database.

Cancellation is cooperative first, followed by a five-second forced kill deadline. Worker parent disconnect requests cleanup. Pause applies empty controls before acknowledging; it stops policy/trainer ticks, **not Minecraft physics or the Java server**. Bots may lose health or be moved while paused. Death/connection failure currently fails the run; add episode recovery to your stage/environment implementation. Shutdown cancels owned workers before stopping owned Java. SIGKILL/power loss cannot guarantee Java cleanup; inspect the PID recorded in your process manager before restarting.

Stages expose observation and reward scaffolds; world preparation is a hook. No legacy NEAT implementation, destructive world-reset command or saved population is migrated automatically. Policies and trainers remain independent from process management and storage. For more stages, add a typed stage ID, stage registry entry, API validation enum and reward/environment implementation.

`packages/agents/src/registry.ts` selects policy/trainer factories for each stage. Agent policy calls run concurrently inside a tick; trainer implementations should batch or serialize updates when needed. You can replace one stage's factories without changing orchestration or the dashboard.

`WorldManager` owns named terrain profiles and saved generations under `SERVER_DIR`. Switching/resetting requires Minecraft to be stopped and no live Minecraft runs queued or supervised. Resets allocate a new level name, leaving all previous terrain, dimensions and player files in place. Profiles persist in `rlcraft-worlds.json`; active selection is read from server properties. Local live run records capture their world generation/settings, and reruns require that selection. Per-episode arena preparation/reset remains an agent-stage hook, separate from manual server-wide world changes.

## Growth path

Declarative arena blueprints are separate from world profiles and starting kits. Submission snapshots the blueprint/placement, checks layout budgets and rejects overlapping queued/active footprints or mixed unrestricted Minecraft runs. Workers request preparation/spawn through parent IPC; the parent supplies the stored specification to the owned Java console. The plugin validates the complete layout, asynchronously loads chunks and applies bounded block writes per tick. It acknowledges completion before agent observations, holds owned agents during episode rebuilding and restores their protection state. Cancellation releases temporary chunk tickets, while placed terrain remains. See [training arenas](arenas.md).

`CloudArchive` separates optional remote archiving from operational storage. SQLite triggers atomically append durable outbox records with run/preset/log/metric changes. A single background exporter sends bounded batches through an `ArchiveSink`, acknowledges successful batches and retains failures across restart. The Firebase adapter uses Firestore for metadata/batched telemetry and object storage for finished artifacts/models. The dashboard reads local live state and exposes archive status; a cloud history reader can be added behind the API later. See [Firebase archiving](firebase.md).

Starting setups are validated against the Minecraft 1.18.1 item catalog and stored in SQLite as reusable presets. Submission copies the setup into the run and its configuration artifact. A worker requests setup only for its own agent; the parent validates ownership, then sends its recorded setup through the owned Java console. The plugin validates the payload before applying it and acknowledges a correlated request. The Minecraft adapter waits for client inventory/player state to synchronise before observing the reward baseline. Episode reapplication uses the same path. This protocol does not grant bots operator permissions or reset terrain. Server preparation runs as a supervised background job, excluding world changes, server startup and live run admission while it is active.

The optional [cloud profile](cloud.md) moves this runtime onto a larger Linux VM without changing local defaults. Data, artifacts and worlds have independent configurable paths, and container images exclude local state/secrets. `RunExecutor` separates worker launch from scheduling; the current implementation and its supervision still use Node subprocesses and IPC.

This is a single-machine foundation with bounded resources, not a distributed scheduler. Before spreading across machines, replace the scheduler transport with a durable broker and leases/heartbeats, move history to PostgreSQL, use object storage for artifacts, and assign each worker to an isolated world/arena with resource quotas. Add authenticated users and access control before exposing the dashboard outside loopback. Add arena allocation before enabling multiple live runs in one shared world. GPU device allocation, model serving, experiment sweeps and automatic checkpoint restore belong behind the existing contracts rather than inside dashboard components.

Prepared infrastructure does not imply improved Minecraft FPS/TPS or training convergence. Compare actual throughput, worker memory and Paper TPS against the same workload before claiming a performance improvement.
